The promise of an AI-built website is speed. You describe the booking page, the chat box, the checkout, and it works. The part that is easy to miss is that "it works" can mean the keys to your payments, your email, and your AI bill have been written into a JavaScript file that every visitor can download. That is not a rare edge case. It is how some popular build tools are designed to behave, and it is what one developer found when a friend finally looked.

## What changed this week

On Wednesday morning, a widely shared post on X from <a href="https://x.com/fromcodetocloud/status/2123062312617804096" target="_blank" rel="noopener">@fromcodetocloud</a> circulated screenshots of a Reddit write-up in r/TechLeader. The author said they had built a booking app over the summer with Cursor and Claude, using Vite, with Stripe for payments, Resend for email, and OpenAI for a small chat helper. They were not a professional developer. Their <code>.env</code> file was listed in <code>.gitignore</code>, so they thought the keys were safe.

A friend who does backend work sat with them for an hour and opened the browser's developer tools. In the JavaScript files the site already served to every visitor, the friend found the live Stripe secret key — the <code>sk_live_</code> one, not the publishable key — along with the Resend key and the OpenAI key, in plain text. The author wrote that Claude had named the variables with a <code>VITE_</code> prefix so the chat would work from the browser. That is not a quirk. Vite's own documentation is blunt: variables prefixed with <code>VITE_</code> are exposed in client-side source code after the project is bundled, and "<a href="https://vite.dev/guide/env-and-mode" target="_blank" rel="noopener">VITE_* variables should not contain sensitive information such as API keys</a>."

The second check was almost a relief. Visiting the site's <code>/.env</code> path did not download the file; the host was only serving the built app. But the author said the server logs showed 212 requests for that file in the two weeks the app had been online, from bots that try it on every site, all day, even though "nobody had even heard of my app yet." The post did not claim those probes had already used the leaked keys. It did say the OpenAI key had no spending limit, that bots were already probing, and that the only thing standing between the author and a bill was that nobody had looked yet.

<Stat num={"212"} cap={"Requests for a /.env file in two weeks, the developer wrote, on an app almost no one had heard of"} />

That night, they wrote, they rotated all three keys — because deleting a key from your code does nothing if someone has already copied it — put a $20 hard cap on OpenAI, and moved the OpenAI and Stripe calls to server-side functions so the browser never touches a secret.

The same day, Senators Maria Cantwell and Mike Rounds <a href="https://www.commerce.senate.gov/press/dem/release/cantwell-rounds-warn-ai-cyber-threats-are-outpacing-u-s-defenses-call-for-urgent-white-house-action-to-protect-critical-infrastructure/" target="_blank" rel="noopener">warned the White House</a> that AI-enabled cyber threats are outpacing defenses. Reuters reported the letter on Wednesday. The point for a small-business site is simpler than the policy debate: if a secret is sitting in a public file, you should assume it will be found quickly.

This is also not the only recent story in which an AI coding tool left a secret in a place the builder did not think to check. Earlier this month, researchers at Apiiro reported that Claude Code settings files — the ones that can store approved shell commands, sometimes with passwords and tokens still inside them — had been <a href="https://arstechnica.com/ai/2026/11/claude-code-settings-files-expose-thousands-of-secrets-on-github/" target="_blank" rel="noopener">turning up in public GitHub repositories</a>.

## Five things to do this week

### 1. Keep secret keys on the server

A Stripe <a href="https://docs.stripe.com/keys" target="_blank" rel="noopener">publishable key</a> (<code>pk_live_</code> or <code>pk_test_</code>) is meant to live in the browser. It can identify your account and help collect payment details. It cannot create charges or read your account data. A Stripe secret key (<code>sk_live_</code> or <code>sk_test_</code>) is the opposite. Stripe treats it like a password: it must stay in your server environment. The same rule holds for a Resend API key, which <a href="https://resend.com/docs/knowledge-base/how-to-handle-api-keys" target="_blank" rel="noopener">Resend says</a> should never be exposed in the browser, and for an OpenAI API key.

If you built the site with Vite, do not put any of those secrets in a variable that starts with <code>VITE_</code>. Vite will copy the value into the files your visitors download, on purpose. The fix is the one Vite recommends: keep secrets on a backend server or in a serverless or edge function, and let the browser call that function, not the payment or email API directly.

A <code>.gitignore</code> entry for <code>.env</code> is necessary. It is not sufficient. The leak in this week's post happened after the <code>.env</code> file itself stayed off GitHub.

### 2. Rotate anything that leaked — immediately

If a secret key has been in a public JavaScript file, a screenshot, a chat, or a repository, treat it as compromised. Deleting it from the next build is not enough. Anyone who already copied it can keep using it until you revoke it.

Stripe's guidance is to <a href="https://docs.stripe.com/keys-best-practices" target="_blank" rel="noopener">rotate a secret or restricted key immediately</a>, even if you are not sure anyone saw it. In the Dashboard, you can rotate a key and choose when the old one expires. There is a grace period of up to seven days so you can switch services without downtime. If the old key was already in a public file, do not leave it valid for a week. Choose an immediate expiration, put the new key only on the server, and then <a href="https://docs.stripe.com/keys" target="_blank" rel="noopener">check that key's request logs</a>.

For Resend, <a href="https://resend.com/docs/knowledge-base/how-to-handle-a-leaked-api-key" target="_blank" rel="noopener">delete the exposed key first</a>, which revokes it at once, then create a replacement and deploy it. Review the Logs and Emails pages for the window the old key was live. Resend keeps 30 days of activity. Do the same at OpenAI: revoke the leaked key, issue a new one, and keep the new one on the server.

### 3. Set usage limits, spend caps, and narrower keys

A leaked key with no cap is a blank check. The developer in this week's post put a $20 hard cap on OpenAI, "not an alert, a cap." That is the right idea. OpenAI lets you set a <a href="https://developers.openai.com/api/docs/guides/spend-limits" target="_blank" rel="noopener">monthly spend limit</a> at the organization or project level and turn on "Enforce a hard limit," so requests start failing instead of the bill just growing. A spend alert only notifies you. It does not stop the traffic.

Stripe does not offer that same kind of monthly spend cap on an API key. What it does offer is almost as important: <a href="https://docs.stripe.com/keys/restricted-api-keys" target="_blank" rel="noopener">restricted keys</a> that have only the permissions a given part of your app needs, and access policies that can limit where those keys can be used. Stripe recommends restricted keys over unrestricted secret keys for new use cases. Resend recommends giving each service its own key and preferring "Sending access" over "Full access," so a leak cannot also read your contacts.

Wherever the provider lets you cap spend or narrow what a key can do, do it today — including on keys you have not leaked. Then look at the last few weeks of logs for anything you did not send.

### 4. Scan the build before you launch, and every time you ship

You do not need special software for the first pass. Build the site. Open the output folder, or open the live site and search the downloaded JavaScript, for <code>sk_live_</code>, <code>sk_test_</code>, <code>rk_live_</code>, and anything else that looks like a secret. The developer in this week's post said the search takes five minutes and wished they had done it before launch, not after.

If the code lives on GitHub, turn on the protections that catch secrets before they are public. <a href="https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning" target="_blank" rel="noopener">Secret scanning</a> already runs automatically on public repositories. <a href="https://docs.github.com/en/code-security/concepts/secret-security/push-protection" target="_blank" rel="noopener">Push protection</a> goes further: it can block a push that contains a supported secret before the secret ever reaches the repository. On GitHub.com, push protection for your own account is on by default for public repositories. If you can enable it on the repository itself, do that too. A scanner is not a complete review, and it will not catch every key, but it is a cheap net under the first mistake.

### 5. Get a second set of eyes on it

The whole story started because a friend who knew backend work spent an hour in a browser. That is the habit. If you built the site with AI, or if a freelancer or a tool built it for you, have someone who did not write the code look at it before you take real payments or send real email.

They do not need a formal audit for this check. They need to open the live site, search the files it already serves, confirm that secret keys are not in those files, confirm that the remaining keys have limits, and look at the dashboards for requests you did not make. If you want a second set of eyes, talk to CC3PO.

## The point

AI will write the feature. It will not, on its own, keep your secret keys out of the files your customers download. A gitignored <code>.env</code> file is not a defense if the build tool is designed to copy those values into the frontend. The bots requesting <code>/.env</code> are already making the rounds.

Open the files your site already serves. Search them. Rotate anything that does not belong there. Then keep the next secret on the server, where it belongs.
